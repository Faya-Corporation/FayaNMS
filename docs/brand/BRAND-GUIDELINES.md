# FayaNMS — Brand Guidelines

**Status:** Phase B2 deliverable · governing document for every FayaNMS brand surface
**Source of truth:** `src/lib/brand/identity.ts` (`FAYANMS_BRAND`) — no surface may construct brand strings, colors or asset paths by hand.
**Companion docs:** [ICONOGRAPHY.md](./ICONOGRAPHY.md) · [ICON-CATALOG.md](./ICON-CATALOG.md) · [ASSET-MANIFEST.md](./ASSET-MANIFEST.md) · [VENDOR-GLYPHS.md](./VENDOR-GLYPHS.md) · [ACCESSIBILITY.md](./ACCESSIBILITY.md) · [SOCIAL-REPOSITORY.md](./SOCIAL-REPOSITORY.md)

## 1. Brand positioning

FayaNMS is an **enterprise network operations management** platform (edition: *Enterprise*).
The brand voice is the product voice — a calm operator's pane of glass (tagline: *"One calm pane of glass for your whole network."*).

| Attribute | What it means for the brand |
|---|---|
| **Enterprise** | Restrained, formal typography and spacing; no marketing hype inside the product surface. |
| **Calm** | Low-chroma neutrals, one primary hue, subtle elevation; alarms use semantics, not decoration. |
| **Precise** | Monospaced technical islands, aligned tabular numerals, exact terminology. |
| **Operational** | The visual language belongs to a NOC: status, density, timelines, topology. |
| **Secure** | Trust cues (shield, ring, audit language) are used sparingly and truthfully — never as fake certification badges. |
| **Multi-vendor** | No single vendor is visually privileged; adapter glyphs are uniform in weight and style. |
| **Evidence-driven** | Claims in brand materials are graded and verifiable (see the README's honest-status pattern). |
| **Data-dense** | The identity must survive 16px table cells and 375px viewports — it is built from simple geometry, not fine detail. |
| **Reliable** | Deterministic rendering: brand assets are static governed files, regenerated by script, never hand-edited. |

### 1.1 What the brand is NOT (anti-patterns)

- **No consumer playfulness** — no mascots, rounded-toy illustrations, emoji in product chrome, or marketing gradients.
- **No neon** — status colors live in the semantic token families; brand surfaces never glow.
- **No gaming aesthetic** — no bevels, chrome, lens flares, or dramatic lighting.
- **No cartoon rendering** — the mark is constructed geometry (nodes inside an operations ring), not an illustration.
- **No vendor dominance** — vendor names/logos never appear in FayaNMS brand assets; adapter glyphs are uniform project glyphs (see [VENDOR-GLYPHS.md](./VENDOR-GLYPHS.md)).

## 2. The three-tier icon architecture

Every visual glyph in the product belongs to exactly one tier. This is the core decision of
the B0/B1 brand work (recorded in [ADR-brand-icon-architecture](../adr/ADR-brand-icon-architecture.md)):

| Tier | Owner | Contents | Examples |
|---|---|---|---|
| **Tier 1 — Brand assets** | `public/brand/` (governed masters) + `src/components/brand/*` | Product mark, mono/white marks, wordmark, lockups, NOC mark, network shield, favicon/app icon, social cards | `fayanms-mark.svg`, `FayanmsLockup` |
| **Tier 2 — FayaNMS domain icons** | `public/icons/fayanms/` (228 governed masters) + `src/components/icons/*` | NMS domain concepts, device types, vendor adapter glyphs, protocols, change/ops/perf/report surfaces, actions, statuses | `devices`, `vendor-cisco`, `config-diff`, `status-online` |
| **Tier 3 — Lucide generic UI + status** | `lucide-react` | Generic controls and chrome (chevrons, close, search, theme, user) and the **existing Lucide-backed status registry** (`src/lib/domain/status.ts` / `status-icon.tsx`) | `ChevronDown`, `X` |

Rules:

- A concept lives in exactly **one** tier. Do not invent a second custom glyph for something Lucide already renders well.
- Tier 2 masters are the **only** custom glyphs; they are consumed through the governed registries (`src/lib/icons/{navigation-icons,vendor-icons,device-icons}.ts`), never by raw `<img src="/icons/fayanms/…">` in ad-hoc code.
- Tier 3 stays for generic controls and status — Lucide was not replaced wholesale (that alternative was evaluated and rejected; see the ADR).

## 3. Logo variant system

| Variant | File (SoT `FAYANMS_BRAND.assets`) | Use |
|---|---|---|
| Primary mark | `fayanms-mark.svg` | App surfaces; the component form (`FayanmsMark`) renders inline with `currentColor`. |
| Primary mark (static brand blue) | `fayanms-mark-brand.svg` | **`<img>`/external contexts that cannot inherit `currentColor`** — README header, docs pages, email (re-audit B1-013). An external `<img>` does not inherit the page's CSS `color`, so `<img src="…/fayanms-mark.svg">` (currentColor) is not reliably brand blue — always use the `-brand` master there. |
| Micro mark | `fayanms-mark-micro.svg` | 16–20 px favicon derivative (B1-014): same ring, **solid** nodes, solid simplified hub, **no connectors** — a deliberate small-size derivative, not a scaled copy. `src/app/icon.svg` and the ICO tiles in `src/app/favicon.ico` derive from it; **the full mark is never rasterized below 32 px**. |
| Mono mark | `fayanms-mark-mono.svg` | Print, export, low-color contexts. Pure black only. |
| White mark | `fayanms-mark-white.svg` | Dark or photographic backgrounds (NOC wallboard, social cards). Pure white only. |
| Wordmark | `fayanms-wordmark.svg` | Standalone wordmark master (regenerable). **In-app the wordmark is real text** via `FayaNMSWordmark` — never an image. |
| Horizontal lockup | `fayanms-lockup-horizontal.svg` | External placements: README header, social, docs covers. |
| Horizontal lockup (white) | `fayanms-lockup-horizontal-white.svg` | Same, on dark backgrounds. |
| Stacked lockup | `fayanms-lockup-stacked.svg` | Square/vertical placements (app icons, avatars, OG cards). |
| NOC mark | `fayanms-noc-mark.svg` | NOC wallboard / operations-center context **only**. It is a sub-brand, **not a second logo**. |
| Network shield | `fayanms-network-shield.svg` | Security / protected-configuration context (encryption, audit). A secondary symbol — **never a logo substitute**. |

### 3.1 Minimum sizes

| Context | Minimum |
|---|---|
| Favicon / app-icon raster | 16 px (micro-mark master; `src/app/favicon.ico` ICO fallback generated by `brand:raster`) |
| Navigation mark | 20 px |
| Inline with text | 24 px |
| Header lockup | 32 px |
| Sign-in surface | 40 px |
| Docs / report covers | 64 px and up |

Below 20 px the ring detail degrades; if a 16–19 px slot is unavoidable, use the micro-mark derivative (`fayanms-mark-micro.svg` / `src/app/icon.svg`), not the full lockup.

**Container vs glyph (B2-019).** The minimums above are *container/tile* sizes; the mark **glyph** inside them is smaller. The `FayaNMSMark` component's named scale is: `xs` 14 (footer), `sm` 20 (nav glyph), `md` 24 (headers), `lg` 32 (loading/report sub-header), `xl` 40 (sign-in glyph), `2xl` 64 (docs/report covers). Concrete mappings: the **sign-in** screen uses a 40px brand **tile** with a 20px **glyph** (`FayaNMSLockup` tiled, `tileSize="lg"`); **docs/report covers** use the 64px glyph (`size="2xl"`); the sidebar/desktop drawer tile is 32px with a 20px glyph (`tileSize="md"`). The minimums in the table are unchanged.

### 3.2 Clear space

Keep a clear zone of **≈ one node diameter** (the diameter of one of the three inner nodes, ~2 units at the 24×24 master scale) on all sides of the mark. Nothing — text, rules, badges, other icons — enters that zone. For lockups, measure from the mark portion of the lockup, not the text.

### 3.3 The "do not" list

Never:

1. **Stretch, skew or rotate** the mark (aspect ratio is fixed; rotation is always 0°).
2. **Add shadows, glows or outlines** to brand assets.
3. **Recolor the mark with status colors** — a red mark does not mean "down"; state is communicated by status components (Tier 2/Tier 3), never by tinting the logo.
4. **Animate the master assets** — the legacy animated `public/logo.svg` template mark was removed from the identity exactly for this reason. Motion near brand surfaces is governed by [ACCESSIBILITY.md §5](./ACCESSIBILITY.md).
5. **Use the Lucide `Waypoints` glyph as the product mark** — it was the pre-B0 temporary placeholder; it must not return as a logo.
6. **Use `public/logo.svg` (the old Z-style template mark) anywhere in product or repository branding** — it is not part of the identity.
7. **Place the mark on busy backgrounds** without the white/mono variant or a plain surface.
8. **Compose new lockups by hand** — the three lockups above are the complete set; adding one is a governance change, not a design decision.
9. **Use the currentColor mark inside `<img>`** — external images cannot inherit CSS color; use `fayanms-mark-brand.svg` for those placements (re-audit B1-013).

### 3.4 Runtime lockup composition (the only sanctioned identity composition)

In app surfaces, identity is composed **only** through `FayaNMSLockup` (`src/components/brand/fayanms-lockup.tsx`). No screen may hand-assemble mark + name from separate pieces. The full sanctioned variant set (re-audit B1-003):

| Variant | Composition | Sanctioned placements |
|---|---|---|
| `compact` | Brand tile with the white mark alone | Collapsed sidebar |
| `tiled` | Brand tile + wordmark + optional descriptor line; `tileSize="md"` (32px tile, 20px glyph, `text-sm` name) for sidebar/mobile drawer, `tileSize="lg"` (40px tile, 20px glyph, `text-lg` name) for sign-in | Desktop sidebar (expanded), mobile drawer, sign-in |
| `horizontal` | Inline mark + wordmark (+ optional descriptor) | Headers, documents |
| `stacked` | Centered mark + wordmark (+ optional descriptor) | Report covers, onboarding |

`descriptorOverride` is the **only sanctioned way to localize or override the descriptor line** (e.g. the translated `nav.brand.subtitle`) — localized text goes through the lockup API, never into a hand-built mark + name row. The mark is decorative whenever the wordmark text is present; a standalone mark names itself via `role="img"` + `aria-label` (see [ACCESSIBILITY.md](./ACCESSIBILITY.md)).

## 4. Brand colors

Values live in `FAYANMS_BRAND.colors` and mirror the semantic design tokens in `src/app/globals.css`
(`--primary`, `--primary-hover`, `--brand-accent`); the hex constants exist for non-CSS consumers
(metadata, SVG masters, OG cards, scripts).

| Token | Light | Dark | Role |
|---|---|---|---|
| Primary | `#2563EB` | same hue (token-driven) | Identity: primary actions, brand surfaces, the mark's home color. |
| Primary hover | `#1D4ED8` | — | Interactive confirmation of primary elements only. |
| Accent | `#0891B2` (dark `#22D3EE`) | brightened for legibility | Sparingly: links, chart emphasis, focus. **Never large backgrounds, never a second logo color.** |

### 4.1 Usage rules

- **Tokens vs hex (B2-018):** in-app components render brand color through the **token classes** (`text-primary`, `bg-primary`, …) — never raw hex. The `FAYANMS_BRAND` hex values exist **only for non-CSS artifacts** (metadata, SVG masters, satori/OG cards, raster scripts). The brand consumer validator (`brand:validate-consumers`, rule R3) fails any raw `#2563EB`/`#0891B2` outside the identity/geometry SoT files.
- **Primary vs accent:** primary owns identity and primary actions; accent is an emphasis tool. They are never blended into gradients for brand surfaces.
- **Social artwork is gradient-free** (B1-007): OG/Twitter cards and the social preview use the **solid primary composition with a separate accent segment** (solid color fields/bars, never a blend). The implementation conforms and `brand:validate` carries a no-gradient guard over `opengraph-image.tsx`, `twitter-image.tsx` and `social-card.tsx`.
- **Semantic status is a separate family and stays separate:** success / warning / danger / danger-orange / info / neutral tokens (`src/lib/domain/status.ts` is the SoT) carry operational meaning. Brand colors never appear *as* status, and status colors never tint brand assets. (The `info` status token happens to share the primary hue `#2563EB` by design — it is still applied through the status token, never by recoloring the mark.)
- The NOC wallboard's fixed dark palette is governed separately by `docs/design-governance.md` and keeps ≥4.5:1 body contrast.
- Manifest / theme colors use **brand primary only** (`theme_color: #2563EB`) — never semantic red/green.
- Charts use the `--chart-1..5` brand-first series; they are data encoding, not brand decoration.

## 5. Governance

- **Masters are governed artifacts.** Additions/changes go through the validation pipeline: `bun run brand:validate` (brand assets), `bun run brand:validate-icons` (icon registry) and `bun run brand:validate-consumers` (consumer scanner) — chained by `brand:audit`; the contracts are specified in [ASSET-MANIFEST.md §5](./ASSET-MANIFEST.md).
- **Mark geometry has a single source:** `src/lib/brand/mark-geometry.ts` feeds the runtime component, the satori/social artwork, the raster generator **and** the static mark-family masters (`mark`, `-brand`, `-micro`, `-mono`, `-white`, plus `public/logo.svg` and `src/app/icon.svg`). Those files are regenerated by `bun run brand:raster` and re-derived byte-for-byte by `brand:validate` — hand edits fail validation.
- **Raster derivatives are generated, not hand-edited:** `bun run brand:raster` produces the app icons, maskable variants, the micro-mark favicon ICO and `github-social-preview.png` via sharp; the validator pixel/byte-compares them (stale derivatives fail).
- **Wordmark/lockup SVGs are flexible typographic templates** (re-audit B2-023): they embed `<text font-family="Inter, 'DejaVu Sans', sans-serif">`, so they may render with a fallback sans-serif when Inter is unavailable and are not guaranteed pixel-identical across systems. They are honest, governed templates — not pixel-deterministic masters.
- Every public brand file is inventoried in [ASSET-MANIFEST.md](./ASSET-MANIFEST.md) with category, usage, minimum size, allowed tones, accessibility role and licensing status ("FayaNMS original project asset").
- Vendor naming and logos are legally bounded by [VENDOR-GLYPHS.md](./VENDOR-GLYPHS.md) — the adapter glyphs are FayaNMS project glyphs, **not** vendor trademarks, and must not be described as such.
